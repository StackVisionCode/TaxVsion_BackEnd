# Investigación de APIs para proveedores de almacenamiento

Fecha de consulta: 19 de octubre de 2026. Se revisaron primero referencias oficiales del proveedor. Esta matriz identifica protocolos y riesgos de integración; no implica que todos deban activarse en la primera entrega.

## Reglas de diseño que se desprenden de las APIs

1. No hay una API uniforme para usar las ocho nubes. Los adaptadores son específicos del proveedor y se deben registrar por capacidad, sin `if/else` del proveedor en handlers de dominio.
2. El flujo actual genera URLs firmadas MinIO y sube al almacenamiento interno antes del escaneo. Conservar ese flujo para archivos operativos; solo después de obtener veredicto `Available` iniciar la copia externa elegida por política. Así un fallo externo no interrumpe el almacenamiento CRM ni antivirus.
3. Persistir para cada copia la identidad de conexión, key/ID remoto, checksum, estado y timestamps. Reintentar por `(TenantId, FileId, ConnectionId, checksum)` para que las entregas RabbitMQ sean idempotentes.
4. Cada Tenant mantiene sus propias conexiones OAuth/credenciales y políticas por propósito. Nunca se comparte una conexión entre tenants. Los tokens se cifran con el protector del backend y no aparecen en respuestas/logs.
5. Separar políticas de archivos operativos, archivos procesados, exports y backups. Los respaldos deben tener jobs y retención independientes y no deben invocar la lógica de OAuth/Drive desde el aggregate de archivos.
6. Tratar revocación, token refresh, rate limit, cuota, outage y `Retry-After` como resultados explícitos del adaptador. Backoff exponencial con jitter solo para errores transitorios; fallar permanentemente ante revocación/credenciales inválidas hasta reconectar.
7. “Otro proveedor futuro” significa poder agregar un nuevo adapter/capability mediante DI y su mapping de autenticación. No significa que un proveedor sin API o autorización comercial vaya a ser conectable automáticamente.
